# 从真实试用里找问题

第一轮 Windows 试用已经完成了一个真实链路：用 DeepSeek 找文件，再说“打开第一份”，确认后 PDF 确实打开。这是用户提供的实际反馈，不是我们用模拟服务替代的验收。原始记录中的私人路径和凭据不收入仓库。

最先卡住的却是配置：CMD 和 PowerShell 的引号不同，密钥复制时带入换行，而程序把请求头构造失败也说成“连接失败或超时”。有一个“已设置”的环境变量，远远不等于模型可用。

现在可以用 `setup` 逐项设置目录和模型；保存前校验并展示范围，失败保留原配置。密钥仍从环境变量读取，首尾空白自动去掉，内部非法字符在联网前报错。`doctor` 默认只做本地检查；显式加 `--check-model` 才用固定样例验证工具调用与结果回传，最多两次请求，不发送本机文件信息。它验证的是协议，不是日常场景的成功率。

试用还暴露了一个状态问题：模型先查到文件，又查了另一个关键词，空结果清掉了快捷入口的编号，但模型还能引用上一轮对象。当时尝试保留上一组编号；后续审核发现数字快捷入口误用旧文件的风险，已在[搜索改进](2026-09-18-search-review.md)中改为清空编号、保留明确对象引用。

还有一个比输出难读更重要的问题。日志中的整机 CPU 不低，但进程 CPU 普遍很小。复查依赖实现并用一个持续计算的测试线程复现后，发现原有 Windows 采样没有正确建立短时差分基线：忙碌线程只报约 0.005%。改用两次累积 CPU 时间的差值后，同一测试约为单核 88.5%。这意味着“有数字”不等于“测对了”，之前由这些进程数值推导的结论需要重新验证。

这一轮也简化了路径、大小、时间和打开回执的显示。资源采样说明按 CPU 还是内存排序；模型被要求先给有证据的简短结论，避免把部分进程解释成全部内存的来源。这些回答习惯仍需真实模型复测，提示改动不是硬性保证。

下一轮在独立试用目录验证小批量移动：查找、选择两项、查看方案、确认、检查实际文件和回执。取消、同名冲突和中途变化也要覆盖。完整的 15 个场景与干净 Windows 分发验收还没有完成。
