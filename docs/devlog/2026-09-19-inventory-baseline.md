# 先测到边界，再决定索引怎么长大

上一轮 Search/Resolve 的四项重点修正已经在当前代码里。本轮重新核对评审，补上了当时延后的移动阻断汇总：例如源目录只读与跨卷限制现在一起报告，不需要用户改完一个配置才发现下一个限制。诊断只读取授权范围内的信息；目标无法核实时会说明相关检查尚未完成，不尝试越权探测。原有确认、执行前复核与移动核验保持不变。

随后开始独立的文件清单实验。它不接入正式 LLM 工具，而是先回答：普通权限下能否保存可查询的文件元数据？重启后还在吗？改名与删除如何反映？原生变化日志能否访问？

## 本机结果

Windows，E 盘 NTFS，debug 构建，自建合成文件夹，不含用户文档。20,000 个小文件加 400 个目录；数据库约 10.52 MB（十进制）。每类查询独立启动进程 30 次，不清除操作系统缓存。测试与其他开发检查并行运行，因此这是开发基线，不是严格性能实验。

| 测量 | 本次结果 |
|---|---:|
| 初次建库 | 2,748 ms |
| 大量匹配的第一页，SQL p50 / p95 | 0.47 / 0.72 ms |
| 唯一稀有匹配，SQL p50 / p95 | 28.76 / 46.44 ms |
| 零结果，SQL p50 / p95 | 27.63 / 32.72 ms |

这里最值得注意的不是第一页快，而是稀有匹配与零结果明显更慢。当前 SQLite 子串匹配仍会遍历元数据。第一页遇到足够结果可以提前结束，因此不能用它的数字宣称“全机几百万文件也只要一毫秒”。SQL 耗时不包含进程启动、数据库打开、输出或模型理解。

目录改名、删除后的完整重扫，重启读取和排除目录联接均通过。单元测试也覆盖预算中止保留上一代、取消不替换快照、不覆盖其他 SQLite 数据库等行为。

USN 探测在本机 C、E 两个 NTFS 卷都得到 `access_denied`，发生在以读取权限打开卷句柄时，Win32 错误码为 5。这个事实只说明当前访问方式在当前进程权限下被拒绝，不说明所有 USN 读取方式均不可用。没有提权、创建日志或改变系统设置。

## 这一步之后

有了一条普通用户可运行的基线，但没有完成实时索引。下一项应该验证原生增量机制与最小权限边界，以及更大规模下的查询结构，不能简单给整个 Shell 管理员权限。后台进程是否必要，也应由这些实验决定。

Tauri 仍是最小桌面入口的候选；暂未创建桌面项目。等第二个入口开始接入，围绕会话隔离和具体操作确认提炼核心接口，不先搭通用 Runtime 框架。三个方向与验收边界已写入 [Roadmap](../../ROADMAP.md) 和 [实验说明](../experiments/file-inventory.md)。

本轮本机 `cargo test --locked --all-targets`：54 项通过、1 项手动 CPU 负载检查忽略；fmt、Clippy 通过。测试中还发现并修复一个 Windows 模拟 HTTP 服务偶发失败：非阻塞 listener 接受的 socket 显式切回阻塞读取，再应用读超时。

45 次真实模型回归、干净 Windows 验证仍未完成。Prompt 对目录局部性、避免全量搜索和资源事实引用的约束也仍需真实模型验证。这些没有因为单元测试通过就被标记为完成。
