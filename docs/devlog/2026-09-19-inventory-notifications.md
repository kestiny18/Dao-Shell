# 普通权限下，文件清单可以继续更新

上一轮 USN 探测被拒绝，不代表更新文件清单必须先把整个 Shell 提升为管理员。本轮验证了另一条更小的路径：监听一个当前用户可读的明确目录，把通知作为“应该重新查看这里”的线索。

已在本机 Windows 的隔离目录跑通：

- 创建、修改和删除普通文件，增量更新对应记录。
- 父目录改名，完整重扫恢复子目录和文件的新路径。
- 强制结束监听进程后修改文件；重启先补扫，能发现停机期间的变化。
- 空闲时也按周期重扫，不依赖每一次变化通知都可靠到达。

这不是 USN 回放，也没有持久事件游标。首次启动先挂监听再建库，运行中每约 200 ms 汇总事件。涉及目录、无法核实的路径或通知丢失时退回全量核对。数据和观察时间一起提交；更新失败不提交半批数据。

一个实际发现是：锁定的 notify 8.2.0 Windows 后端并不能让我们承诺“原生缓冲区溢出一定有 Rescan 回调”。我们自己的有界队列能检测满队列，库显式给出的错误也能处理，但仍需要周期重扫修复静默遗漏。若后端订阅失效，本实验尚未自动重建订阅，周期扫描是兜底，而非实时保证。

本轮测试不包含制造真实原生缓冲区溢出。单元测试覆盖注入溢出/Rescan/Error、增量身份刷新、删除、部分批次回滚及超预算回滚。原生 smoke 测试使用隐藏的短期实验进程，结束后没有常驻进程遗留。

阶段判断：明确用户目录的索引更新可以先在普通权限下成立；系统级 MFT/USN 索引仍是独立问题，不应成为最小桌面入口的前置条件。接下来可以开始 Tauri 的最小文件入口，再由这个真实调用方推动会话与共享能力的接口边界。此时还不需要独立服务、SDK 或全机写权限。

运行说明见 [索引实验](../experiments/file-inventory.md)。本机自动化测试 56 项通过、1 项手动 CPU 测试忽略；Clippy 通过。样本结果证明的是目录级功能，不是百万文件性能。
