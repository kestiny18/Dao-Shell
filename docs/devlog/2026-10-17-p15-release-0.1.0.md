## Findings and changes

The initial remote Windows run [38757607895](https://github.com/kestiny18/Dao-Shell/actions/runs/38757607895) reports the ordinary IPC test failed, then the entire core test process exited with `0xc0000409`. It did not capture the original panic. A clean local GNU baseline reproduced neither failure: 100 core library tests passed, 2 helper tests ignored.

The IPC implementation uses synchronous `PIPE_NOWAIT` handles and null OVERLAPPED arguments; no pending overlapped stack buffer/cancellation lifetime was found. The ordinary IPC test explicitly asserts a non-elevated process token, and the production fixture worker independently rejects elevation. Hosted runner elevation is a hypothesis for the remote failure until the main Agent's new TokenElevation-only CI diagnostic and uncaptured failures confirm it. A failed worker would also make `Running::start` time out, and its old Drop unwrapped the same worker error while already unwinding, causing a second panic/abort. This test cleanup flaw is directly verified with a synthetic worker error and original panic regression.

Changes remain test-only:

- `src/file_index/worker/tests.rs`: ordinary fixture tests re-execute their exact existing body in a restricted child when the host token is elevated. The ordinary-token assertion, live authentication, pagination/replay, mutation/restart, permission-denied visibility, expiry, rebuild and crash-recovery checks remain. The ordinary volume refusal test is also kept under an ordinary token. A separate regression always exercises the restricted launcher even on a normal host. A host-elevated-only assertion verifies fixture refusal before database creation; no elevation is requested by tests. Cleanup always cancels/joins the worker, reports errors outside unwinding, and preserves the first panic during unwinding.
- `src/file_index/worker/tests/ordinary_token.rs`: a small test helper uses the caller's own process token with `CreateRestrictedToken(LUA_TOKEN | DISABLE_MAX_PRIVILEGE)`, checks actual `TokenElevation == 0`, and uses `CreateProcessAsUserW` for the exact test executable/name. It captures synthetic test output, checks successful exit and one executed test, and bounds waiting. Timeout cleanup can terminate only the exact child handle created by this helper. There is no account provisioning, policy change, token text substitution or UAC. API/token/launch failure is a failed test, never a skip or elevated fallback.
- `desktop/src-tauri/src/app_actions.rs`: the existing shortcut fixture compares canonical target paths and exact file-object identity instead of requiring Windows Shell's expanded path spelling to equal an 8.3 TEMP spelling. The CI log proves the short/long representation difference. Existing argument rejection and changed-shortcut/no-dispatch assertions remain; production shortcut resolution/actions are unchanged.

The restricted-token APIs and privilege exception are documented by Microsoft: [CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken), [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw). The helper requests only TOKEN_QUERY, TOKEN_DUPLICATE and TOKEN_ASSIGN_PRIMARY, without enabling new privileges.

## Diagnostic-first checkpoint after repeated startup failure

The second remote correction [run 39030821169](https://github.com/kestiny18/Dao-Shell/actions/runs/39030821169), Windows job `117390737033`, still reports seven pre-harness `0xc0000142` failures (96 passed / 7 failed / 2 ignored). Therefore the preceding desktop/handle correction is not considered a verified fix. Product and existing launcher code are frozen while the failure is investigated. No further guessed desktop/token replacement is made.

Added diagnostic-only `scripts/diagnose-ci-windows-child.ps1`, invoked by the main Agent's separate workflow_dispatch job. Four cases use the original process token, the current LUA/disallowed-privilege token, SAFER NORMALUSER, and explicit Administrators deny-only with maximum privileges disabled. Each launches only the fixed System32 `cmd.exe /d /c exit 0`; an optional validated built core test harness can be listed with `--list`, without executing tests or runtime actions. The script reports token category, elevation/admin/session booleans, integrity RID, numeric API errors, exit status, timeouts and output byte counts. It does not report raw account/SID/path/token data or child output. Per-child waits are bounded at ten seconds and timeout cleanup holds only exact child handles.

The probe reads current station/desktop names internally, impersonates the candidate token only on the calling C# thread, attempts read-only opens, closes those handles, and reverts in finally. Failed impersonation never proceeds; failed reversion terminates the diagnostic host. It does not switch the process window station, create accounts, adjust host ACLs/policies, enable privileges, install anything or change the production authorization guard.

Local normal-token sanity: all four token cases created successfully, reported non-elevated/no enabled Administrators group/medium integrity/same session/station and desktop read access, and SystemCmd exited zero without timeout. The optional Rust harness was NOT_RUN in this first sanity pass. Evidence: `.tools/release-0.1.0-20261017/local-child-probe.log`. This is probe validity evidence, not evidence for the elevated-host failure; the next remote diagnostic is required.

Primary documentation recheck: the current [CreateRestrictedToken flags documentation](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken) explicitly documents LUA_TOKEN 0x4 (unsupported on XP/Server 2003), so an assumption that it is reserved is not a supported diagnosis. [SaferCreateLevel](https://learn.microsoft.com/en-us/windows/win32/api/winsafer/nf-winsafer-safercreatelevel) and [SaferComputeTokenFromLevel](https://learn.microsoft.com/en-us/windows/win32/api/winsafer/nf-winsafer-safercomputetokenfromlevel) document the NORMALUSER comparison case. ## Token flag diagnostic matrix

The [first dedicated remote probe, run 39031327248](https://github.com/kestiny18/Dao-Shell/actions/runs/39031327248), confirms the failure also occurs when launching a fixed system command, before any Rust harness or IPC. Its result is diagnostic evidence, not a release CI pass:

| Token case | Elevated | Administrators enabled | Integrity RID | SystemCmd exit |
| --- | --- | --- | --- | --- |
| Original | true | true | 12288 | 0 |
| LUA + DISABLE_MAX_PRIVILEGE | false | false | 12288 | 0xC0000142 |
| SAFER NORMALUSER | true | false | 12288 | 0 |
| Administrators deny-only + DISABLE_MAX_PRIVILEGE | true | false | 12288 | 0xC0000142 |

All four remained in the same session, could open the current station/desktop for read access, and had no token API error or timeout. This rules out a Rust-specific startup defect and a simple read-access denial, but does not yet establish which startup component rejects the token. SAFER alone is not an acceptable fixture replacement because its actual elevation bit remains true and the existing production fixture guard must still reject it.

The next diagnostic-only change retains these controls and adds LUA-only, DISABLE_MAX_PRIVILEGE-only, LUA+DISABLE_MAX_PRIVILEGE with only the newly created token lowered to medium integrity, and SAFER followed by LUA+DISABLE_MAX_PRIVILEGE. These distinguish the privilege-removal flag, LUA behavior and inherited high integrity; they are comparisons, not proposed production changes. Full-rights station/desktop opens are recorded as booleans/errors as an additional ACL check; no object mutation API is called. TOKEN_ADJUST_DEFAULT access is requested only to set the new comparison token's integrity label. The original host token, privileges, policy and object ACLs are not changed, and the code refuses to raise an existing lower integrity level.
