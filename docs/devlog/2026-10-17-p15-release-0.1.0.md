## Findings and changes

The initial remote Windows run [38757607895](https://github.com/kestiny18/Dao-Shell/actions/runs/38757607895) reports the ordinary IPC test failed, then the entire core test process exited with `0xc0000409`. It did not capture the original panic. A clean local GNU baseline reproduced neither failure: 100 core library tests passed, 2 helper tests ignored.

The IPC implementation uses synchronous `PIPE_NOWAIT` handles and null OVERLAPPED arguments; no pending overlapped stack buffer/cancellation lifetime was found. The ordinary IPC test explicitly asserts a non-elevated process token, and the production fixture worker independently rejects elevation. Hosted runner elevation is a hypothesis for the remote failure until the main Agent's new TokenElevation-only CI diagnostic and uncaptured failures confirm it. A failed worker would also make `Running::start` time out, and its old Drop unwrapped the same worker error while already unwinding, causing a second panic/abort. This test cleanup flaw is directly verified with a synthetic worker error and original panic regression.

Changes remain test-only:

- `src/file_index/worker/tests.rs`: ordinary fixture tests re-execute their exact existing body in a restricted child when the host token is elevated. The ordinary-token assertion, live authentication, pagination/replay, mutation/restart, permission-denied visibility, expiry, rebuild and crash-recovery checks remain. The ordinary volume refusal test is also kept under an ordinary token. A separate regression always exercises the restricted launcher even on a normal host. A host-elevated-only assertion verifies fixture refusal before database creation; no elevation is requested by tests. Cleanup always cancels/joins the worker, reports errors outside unwinding, and preserves the first panic during unwinding.
- `src/file_index/worker/tests/ordinary_token.rs`: a small test helper uses the caller's own process token with `CreateRestrictedToken(LUA_TOKEN | DISABLE_MAX_PRIVILEGE)`, checks actual `TokenElevation == 0`, and uses `CreateProcessAsUserW` for the exact test executable/name. It captures synthetic test output, checks successful exit and one executed test, and bounds waiting. Timeout cleanup can terminate only the exact child handle created by this helper. There is no account provisioning, policy change, token text substitution or UAC. API/token/launch failure is a failed test, never a skip or elevated fallback.
- `desktop/src-tauri/src/app_actions.rs`: the existing shortcut fixture compares canonical target paths and exact file-object identity instead of requiring Windows Shell's expanded path spelling to equal an 8.3 TEMP spelling. The CI log proves the short/long representation difference. Existing argument rejection and changed-shortcut/no-dispatch assertions remain; production shortcut resolution/actions are unchanged.

The restricted-token APIs and privilege exception are documented by Microsoft: [CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken), [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw). The helper requests only TOKEN_QUERY, TOKEN_DUPLICATE and TOKEN_ASSIGN_PRIMARY, without enabling new privileges.

## Default-descriptor diagnostic comparison

The [second dedicated probe, run 39031528414](https://github.com/kestiny18/Dao-Shell/actions/runs/39031528414), narrowed the elevated-host failure further. LUA-only still failed with 0xC0000142; DISABLE_MAX_PRIVILEGE-only remained elevated/admin-enabled and started successfully. Lowering the new LUA+DISABLE_MAX_PRIVILEGE token to medium integrity did not change the failure. Full-rights opens of both current station and desktop succeeded, and the SAFER→LUA chain failed process creation with 1314. Thus none of removing DISABLE_MAX alone, lowering integrity or granting existing desktop/station rights is an evidence-backed fix.

The next bounded diagnostic adds token-owner/default-DACL booleans for all cases, without exposing SID/SDDL values. It compares two new LUA+DISABLE_MAX cases: `LuaOwnProcessThreadDacl` supplies explicit SECURITY_ATTRIBUTES only for the new child process/thread; `LuaUserDefaultDacl` changes only the newly created comparison token's default DACL. Each uses a protected descriptor granting full access solely to the token's actual user and SYSTEM. Existing host/process/file/window-station/desktop ACLs are unchanged. The two cases distinguish access to the child's initial objects from default security of later objects. This is an unproven diagnostic hypothesis until elevated-host startup succeeds.

[CreateProcessAsUserW process/thread attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw) documents defaults from the user referenced by hToken; [TOKEN_DEFAULT_DACL](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-token_default_dacl) describes the token ACL used for newly created objects. The hypothesis is specifically an inherited default descriptor unusable after admin group filtering, not a claim that defaults always come directly from the parent process.

Local ordinary-host sanity (`local-token-dacl-probe.log`): all original normal-host successful cases and both new descriptor cases started SystemCmd with exit 0. The chained SAFER case still failed creation with 1314. Here each token's owner equals its user; default DACLs explicitly allow user full access and SYSTEM, without a direct Administrators ACE. These facts explain why this local host cannot reproduce an elevated-only default-descriptor defect, but do not prove that hypothesis on the runner. Script parsing/Add-Type/execution and `git diff --check` passed. No launcher or production change was made; Coder writes stop pending the next remote comparison. The main Agent retains commit/dispatch/release responsibility; independent testing/review remain NOT_RUN.

## Causal result and fixture correction

The [third dedicated probe, run 39031740945](https://github.com/kestiny18/Dao-Shell/actions/runs/39031740945), provides the distinguishing result. On the elevated runner, original/LUA token default DACLs did not explicitly allow the user. The LUA token had its user as owner and was non-elevated/admin-disabled, yet SystemCmd still failed 0xC0000142. Explicit attributes on only its new initial process/thread also failed. Changing only that new restricted token's default DACL to the actual user plus SYSTEM produced a non-elevated/admin-disabled token with user full access, and SystemCmd exited 0. This identifies the inherited token default DACL as the actionable fixture construction defect; it is not fixed by substituting an elevated SAFER token, changing integrity or relaxing production checks. No claim is made about which individual Windows initialization object first rejected access.

Based on that remote comparison, `tests/ordinary_token.rs` now normalizes only the newly created restricted token's default DACL before launch. The protected ACL has exactly the actual current-user SID and SYSTEM with generic full access, with no Administrators/Everyone grant. TOKEN_ADJUST_DEFAULT is requested so the newly created handle can set TokenDefaultDacl. Every SetTokenInformation target is that new limited token; the host token and existing process/file/station/desktop ACLs remain unchanged. The actual non-elevated check still runs after normalization, and all production worker/authentication/identity/cancellation guards are unchanged.

Added `restricted_child_preserves_snapshot_after_nested_crash`: it forces the existing real crash-recovery fixture inside the restricted child, including a second child process that exits with an uncommitted SQLite transaction, then verifies the original publication after restarting the worker. Together with the forced live IPC test, this checks real child and nested-child startup plus persistence, not merely launcher success.
