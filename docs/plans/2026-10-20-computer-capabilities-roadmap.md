## 1. 目标与当前依据

把桌面聊天从文件入口扩展为“了解电脑 → 找到具体对象 → 明确操作 → 核验结果”的入口。继续优先 Windows 普通用户权限，以当前请求为执行边界。

本次只读检查基于 HEAD `c7780ab` 与当时工作区；工作区有既存索引、设置和试用记录改动，本方案不修改这些内容。检查了产品文档、工作流和相关代码，没有运行构建、真实模型或电脑操作测试。

现状：

- `src/dialogue.rs` 的桌面入口只保留 `file_search/file_inspect/file_open`；不是采集器全部缺失。
- `src/capabilities.rs`、`src/runtime.rs` 已有 CLI 的 `resource_snapshot/process_list`。
- `src/resources.rs` 已有 CPU、内存、磁盘空间、进程短时采样及 CPU/内存排行。
- `src/computer.rs` 已组合资源、网络接口流量、设备和注册应用。网络接口有 IP 不等于互联网可用；应用清单不完全覆盖 Store 和便携程序。
- `src/profile.rs` 有电脑档案；桌面概览可主动发送裁剪后的资源事实给模型解释。
- `desktop/src-tauri/src/app_actions.rs` 已有严格解析的本地应用动作；`process_actions.rs` 与核心 `process_control` 已有实例身份核验和本地结束确认。它们目前不向模型开放。
- `src/session.rs` 的 `FileSession/Reply` 及候选展示以文件为中心，不能只增加工具 schema 就认为聊天接入完成。

## 2. 分期与优先级

### 第一期：自然语言只读查询（第一个交付）

目标：用户不切换到概览也能问电脑状态，并沿同一批真实结果追问。

| 能力 | 首期范围 | 示例 |
| --- | --- | --- |
| CPU、内存 | 当前短时采样、CPU/内存排行、明确指标口径 | “现在内存用了多少？谁占得最多？” |
| 磁盘 | 各盘容量、可用空间；不做全盘空间归因扫描 | “C 盘还剩多少空间？” |
| 网络 | 接口、配置状态、短时收发速率及观测局限 | “现在网络流量大吗？” |
| 运行对象 | 原始进程查询、筛选、排序；可靠匹配时归并为应用 | “哪些程序正在运行？” |
| 已安装应用 | 按名称/发布者筛选、版本、登记大小及覆盖范围 | “装了几个 Python 版本？” |
| 电脑档案 | 系统版本、CPU、内存、运行时长等已有可用字段 | “这台电脑什么配置？” |
| 基础解释 | 仅基于采样事实说明资源压力和可选下一步 | “现在电脑为什么可能卡？” |

设计要求：

- 按需查询各域；问 CPU 不枚举全部软件或刷新全部概览。默认有界结果，支持分页/筛选，不把全机数据塞进上下文。
- “正在运行的应用”与“进程”分别呈现；多进程应用只在身份映射可靠时合并，匹配失败标未知，后台进程不冒充可见窗口。
- 返回采样时间、时间窗口、来源、完整/部分覆盖、未知值；高占用不直接证明卡顿根因。
- 同一回答中的 CPU/内存比较使用同一采样；追问明确引用旧样本或重新采集，不能无提示混用。
- 本地过滤后才发送所需字段给模型；默认不发送完整应用目录、命令行、环境变量、窗口标题、MAC 和完整 IP。
- 首次启用电脑查询时说明哪些事实会发送到所选模型，并保存本地选择。文件访问权限不自动授予新增的系统信息共享权限。
- 无模型/模型故障时保留本地状态入口和明确错误，电脑问题不能静默退化成文件名搜索。

验收：六类查询及跨轮追问可用；数据失败/权限不足如实呈现；模型不能调用未启用能力；没有任何新增启动、结束或系统修改路径。

### 第二期：启动和停止应用（第二个交付）

目标：完成“查找对象 → 预览具体动作 → 本地确认 → 执行 → 回执”的闭环。

- 启动：复用当前可信开始菜单入口解析，先支持普通权限、无自定义参数的已识别桌面程序。名称多候选先消歧，缺入口明确不支持，不猜 EXE 路径。
- 正常关闭：对可核验、属于当前用户的窗口应用发送关闭请求；保留应用自己的保存提示，不代点、不超时升级为强杀。
- 强制结束：单独动作，复用现有实例身份与保护规则；确认中列出本次全部目标、实例数及未保存内容丢失风险。不顺带结束新实例、子进程或同名对象。
- 启动、正常关闭、强制结束均由本地动作卡确认；模型参数不接受 `confirmed=true` 等授权字段。只读查询不逐次确认。
- “重启应用”暂不作为原子工具：先呈现关闭/结束与重新启动的步骤及条件；前一步结果未知或未退出时不自动启动下一步。
- 每次执行前复核目标身份和权限；进程不能只靠 PID/名字，必须包括创建时间和必要的用户/映像身份；启动复核入口与目标文件身份。
- 请求被系统接受、观察到进程、窗口出现是不同事实。正常关闭可能仍在等待保存；不能用退出码或模型回答推断成功。
- 多会话确认、切换/删除会话、取消、刷新、重启不产生跨会话授权；已执行结果不因取消而改写；未知结果先核对，不自动重试。

暂不向模型开放管理员启动、任意参数、命令解释器、批量结束、服务控制、安装卸载、计划任务。现有显式 UI 功能保留自己的边界。

验收：专用测试应用覆盖重名、多实例、PID 复用、目标替换、退出竞态、保存对话框、拒绝/取消、重复确认、受保护对象和未知结果。开发自测先用模拟 provider 与受控测试子进程，禁止以真实办公软件及未保存文档试杀。

### 第三期：短时诊断与覆盖补齐

详细计划与方案：[第三期诊断设计](2026-10-22-phase3-diagnostics-design.md)。2026-10-22 经用户批准实施并完成[本机原型与自测交付](../devlog/2026-10-22-phase3-diagnostics.md)，支持范围及未验证项以该候选记录为准；第二期正常关闭仍独立 BLOCKED。

依据前两期反馈排序，每项单独形成小闭环，不整包承诺：

1. 用户明确发起的 30–60 秒观测：CPU/内存/网络变化及对比，可取消、到时结束，默认仅会话内保留。
2. 网络诊断：将本地接口、默认路由、DNS、用户指定目标的可达性分开；外部探测明确目标和会产生网络请求，不把失败直接解释为“断网”。
3. 进程磁盘 I/O、GPU/显存、电池与电源状态：先做 Windows 数据可用性小实验，字段不可得返回未知。
4. Store 应用、便携应用与多入口匹配：提升发现/启动覆盖，来源和可信入口分开建模。
5. 开机启动项只读查看、固定 Windows 设置页跳转；修改留到独立任务。

验收：诊断证据足以复查、观测有资源预算；不把时间相关性当因果，不自动执行修复建议。

### 第四期：经验证的维护动作（按需求选择）

详细计划与方案：[第四期维护设计](2026-10-22-phase4-maintenance-design.md)。2026-10-22 已明确 4A–4D 分批范围和完成条件，尚未实施，不授权真实装卸或设置修改。

候选：用户明确选择的软件安装/升级/卸载、启动项修改、特定网络设置修复。各自有独立 Plan、权限、执行与核验方案。安装操作需要来源/版本/已有安装消歧；卸载不能把注册表字符串直接当指令执行。

持续监控、告警和后台自动处理作为另一个产品决策：先验证用户需要、退出行为、保留周期和成本，再考虑后台执行。暂不做“自动优化电脑”、通用 Shell 或任意脚本工具。

## 3. 架构调整

结论：需要做一次适度的核心收拢；不需要为本次扩展重写项目或再建通用 Agent 平台。

建议调用结构：

```text
桌面聊天 / 概览 / CLI
          ↓
Session：上下文、当前对象、请求取消、确认归属
          ↓
Capability Catalog + Runtime 调度与策略检查
          ├── 只读查询 → Resource / Network / App / Profile 服务
          └── 动作准备 → 本地确认 → 再核验 → 执行 → 回执
                                  ↓
                     Windows provider / 已有资源采集器
```

### 3.1 第一期必须完成

- 保留现有核心 `Runtime`，增加能力元数据：可用入口、只读/动作、所需权限、参数/结果契约。由同一能力目录导出模型 schema、运行时准入与可用性描述，消除“六个工具”“桌面文件入口”等硬编码相互漂移。动态工具选择不能替代执行端检查。
- 从 `computer::overview` 提炼可单独调用的资源、网络、应用查询；概览成为组合消费者。先使用少量明确模块/函数，不为每个查询引入 trait。
- 给结果增加公共观测信封：`observation_id`、`observed_at`、`sample_window`、`source`、`coverage`、`limits`、`data`。静态信息无采样窗口时明确不适用；部分失败按域保留已获得事实。
- 将会话的结果载体扩展为带类型的文件/进程/应用/状态结果；文件编号与应用、进程引用隔离，不能一次查询覆盖另一域的对象。保留现有文件交互兼容性。
- 第一期开头用兼容包装引入电脑会话行为；避免一边扩能力一边大规模改名。通用 `Session` 命名可以在行为稳定后整理。
- 继续按请求采样；短 TTL 缓存仅用于应用目录/静态档案，标日期且支持刷新。实时问题优先新采样，失败保留的旧值必须显著标旧。
- 分离文件目录权限、系统信息共享权限与应用动作权限；“完全文件访问”不意味能够结束所有进程。

### 3.2 第二期必须完成

- 将桌面 `app_actions/process_actions` 内可复用的目标解析、计划和执行语义逐步移入核心；Tauri bridge 保留确认 UI、事件与会话绑定，不复制另一套模型专用执行器。
- 使用会话隔离的对象引用和待确认计划。共享发现缓存可以复用，动作引用不能由全局概览刷新悄悄转绑；失效必须明确返回。
- 不可变计划至少记录：动作类型、精确目标与身份、范围、风险、有效期、会话/请求。确认只能由本地交互通道提交，一次消费；执行前再次核验。
- 统一必要的动作回执和状态：取消、拒绝、请求已接受、待观察、已观察完成、失败、未知。读取类观测不必写入持久日志；动作日志仅保存最小核验事实，避免留下完整敏感清单。
- 初期保留现有全局动作准入/互斥，正确处理等待确认和取消。只有证据表明互斥妨碍体验时再拆读写并发与锁粒度，不与第一期同时重构调度器。

### 3.3 暂不引入

- 新的常驻电脑管理 daemon、通用插件系统、SDK、消息总线和工作流引擎。
- 把现有管理员索引服务变成通用应用/进程控制服务。索引服务继续专职名称发现，交互动作运行在普通用户上下文。
- 全量长期进程数据库或持续把电脑状态上传给模型。

只有退出 UI 后仍需观测、多客户端共享状态或明确的最小权限任务需要时，才单独评估后台服务及其 IPC 边界。

## 4. 工具划分建议

名称是设计建议，实施时确认兼容性；不按每个指标拆一个工具，也不提供任意 command/action 字符串。

| 工具 | 用途 | 阶段 |
| --- | --- | --- |
| `resource_snapshot` | CPU/内存/磁盘及同窗排行；复用已有契约 | 一 |
| `process_list` | 有界进程筛选/排序 | 一 |
| `network_snapshot` | 接口与短时收发状态 | 一 |
| `app_list` | 登记应用、可靠运行匹配、版本与覆盖 | 一 |
| `computer_profile` | 静态配置与系统信息 | 一 |
| `app_launch` | 以已观察引用准备启动确认 | 二 |
| `app_close` | 以已观察引用准备正常关闭确认 | 二 |
| `process_terminate` | 以精确实例引用准备强制结束确认 | 二 |

动作工具的模型入口只负责请求/准备；本地交互控制确认与执行。工具响应与 UI 事件协议必须支持等待、取消与最终回执，不能将“方案已准备”显示成“已执行”。

## 5. 实施顺序与检查

1. T1：整理能力目录、结果契约和权限；保持现有文件行为。
2. T2：接入五个只读工具与按需采集，补数据裁剪、未知/旧样本/分页。
3. T3：完成桌面状态结果与追问、无模型退路，交付第一期原型。
4. T4：收拢应用动作核心和会话隔离确认，先交付启动。
5. T5：分别实现正常关闭与强制结束，完成第二期原型。
6. 再按真实使用频率选择第三期的一项，不直接并行展开全部电脑管理功能。

每步运行受影响的 Rust、桌面桥接/UI 测试及必要构建；保留文件搜索/打开回归。授权、身份、取消和持久化边界补确定性测试；模型协议用模拟响应，自然语言能力另跑指定真实模型用例并记录模型/版本与结果。

第一期建议固定至少 12 个只读问题（六类各两条）及三组跨域追问；第二期用专用测试应用验证动作边界。不以成功率抵消一次误目标或未确认执行。

独立测试与评审按用户触发；推荐在第二期用于真实日常应用前检查确认归属、身份竞态与回执真实性，不自动启动角色。本方案不提供未经实测的工期承诺，也不改变已有索引试用任务的状态。

## 6. 当前建议

先批准第一期只读能力接入，第二期作为紧接的应用操作闭环。这样可先验证用户如何用自然语言查询和追问，再在同一对象/事实模型上增加动作。第一期不以全面覆盖所有软件、完整故障诊断或后台自主维护为完成条件。
